Electrical rules checking (ERC) is the automated verification step applied to a [[schematic]] document, in which a CAD package tests the drawn connectivity against a set of rules describing which pin types may legally connect to which.<sup class="cite"><a href="#src-953" title="EEVblog #953 - What Is Schematic ERC?">953</a></sup><sup class="cite"><a href="#src-1193" title="EEVblog #1193 - KiCAD PCB 4 Layer Swapping &amp; Stackup">1193</a></sup> It is the schematic-side counterpart of [[design-rule-checking|design rule checking]] (DRC), which operates on the [[pcb|PCB]]: ERC is for schematics, DRC is for boards.<sup class="cite"><a href="#src-1193" title="EEVblog #1193 - KiCAD PCB 4 Layer Swapping &amp; Stackup">1193</a></sup> Its value lies in catching connectivity errors at the cheapest possible point in the flow, because an error missed in the schematic propagates into the netlist, into the routed board, and into fabricated hardware — potentially weeks or months later, when the fault is finally found in a prototype that should never have been built.<sup class="cite"><a href="#src-953" title="EEVblog #953 - What Is Schematic ERC?">953</a></sup>

## Position in the design flow

Designing a board is a multi-step process: draw the schematic, run the ERC, lay out the PCB, run the DRC, generate manufacturing files, then have the board assembled.<sup class="cite"><a href="#src-1307" title="EEVblog #1307 - TUTORIAL: PCB BOM Consolidation">1307</a></sup> ERC therefore sits at the first gate, before any layout effort is committed.<sup class="cite"><a href="#src-1307" title="EEVblog #1307 - TUTORIAL: PCB BOM Consolidation">1307</a></sup><sup class="cite"><a href="#src-953" title="EEVblog #953 - What Is Schematic ERC?">953</a></sup> Running it should be a matter of course rather than an optional extra.<sup class="cite"><a href="#src-953" title="EEVblog #953 - What Is Schematic ERC?">953</a></sup>

The consequences of skipping it are concrete. A schematic drawn with a mismatched snap grid can leave a pin visually touching a wire without actually making an electrical connection; that missing connection never reaches the netlist, never reaches the PCB, and the pin simply goes unrouted, producing a board that does not work.<sup class="cite"><a href="#src-1129" title="EEVblog #1129 - Creating a Nice Readable Schematic">1129</a></sup><sup class="cite"><a href="#src-953" title="EEVblog #953 - What Is Schematic ERC?">953</a></sup> Setting snap grids correctly before drawing is the first defence, and ERC is the check that catches what the grid discipline misses.<sup class="cite"><a href="#src-1129" title="EEVblog #1129 - Creating a Nice Readable Schematic">1129</a></sup>

## What the check finds

The rule set is expressed as a connection matrix: every combination of pin types — input, output, open collector, power, tri-state, bus — is mapped to an outcome, and each outcome can be set independently to no report, warning, error, or fatal error.<sup class="cite"><a href="#src-953" title="EEVblog #953 - What Is Schematic ERC?">953</a></sup><sup class="cite"><a href="#src-255" title="EEVblog #255 - DIPtrace PCB CAD - First Impressions">255</a></sup> This makes the tool tunable; a schematic generating a flood of nuisance warnings can have specific checks switched off deliberately.<sup class="cite"><a href="#src-255" title="EEVblog #255 - DIPtrace PCB CAD - First Impressions">255</a></sup>

Errors typically caught include two output pins shorted together, an output pin connected to a power net such as [[ground]], and inputs tied together with nothing driving them — the "no driving source" class of fault.<sup class="cite"><a href="#src-5eJorvyA708" title="Altium Designer Serious ERC bug">•</a></sup><sup class="cite"><a href="#src-953" title="EEVblog #953 - What Is Schematic ERC?">953</a></sup><sup class="cite"><a href="#src-253" title="EEVblog #253 - KiCAD Install &amp; Schematic - First Impressions">253</a></sup> In KiCad the same condition is reported as a type three error, a pin connected to some other pins but no pin to drive it.<sup class="cite"><a href="#src-253" title="EEVblog #253 - KiCAD Install &amp; Schematic - First Impressions">253</a></sup> Beyond raw connectivity, a capable package extends the checks to buses, code symbols, sub-parts of multi-part components, configurations, harnesses, and net-level issues.<sup class="cite"><a href="#src-953" title="EEVblog #953 - What Is Schematic ERC?">953</a></sup>

Warnings are not all equal. Hidden power pins on parts such as the 74HC series will generate hidden-net-added notices for VCC and ground that carry no real meaning and can be dismissed.<sup class="cite"><a href="#src-953" title="EEVblog #953 - What Is Schematic ERC?">953</a></sup><sup class="cite"><a href="#src-952" title="EEVblog #952 - Nixie Tube Display Project - Part 3">952</a></sup>

## Invocation and reporting

In Altium Designer the ERC is reached either by compiling the individual schematic document or by compiling the entire PCB project; compiling the project is the recommended route.<sup class="cite"><a href="#src-953" title="EEVblog #953 - What Is Schematic ERC?">953</a></sup> The term "compile" is simply another name for running an electrical rules check, and the analogy is deliberate — the schematic has been drawn, and compilation reports whether something stupid has been done.<sup class="cite"><a href="#src-953" title="EEVblog #953 - What Is Schematic ERC?">953</a></sup> The check can also be bound into an output job so the report is generated alongside other outputs, as HTML or as a PDF suitable for circulation.<sup class="cite"><a href="#src-953" title="EEVblog #953 - What Is Schematic ERC?">953</a></sup>

Other packages present the same idea under their own names. DIPtrace places ERC on F9 with an electrical rule setup dialog structurally identical to Altium's, and runs effectively instantly.<sup class="cite"><a href="#src-255" title="EEVblog #255 - DIPtrace PCB CAD - First Impressions">255</a></sup> KiCad exposes ERC alongside the netlist and BOM generators, and additionally places an ERC marker on the schematic as a graphical object, which is unusual — the markers must be erased from the page after the underlying errors are resolved.<sup class="cite"><a href="#src-253" title="EEVblog #253 - KiCAD Install &amp; Schematic - First Impressions">253</a></sup>

## Zero errors as a gate

The working goal is to drive all errors and warnings to zero before proceeding to [[pcb-layout|PCB layout]].<sup class="cite"><a href="#src-953" title="EEVblog #953 - What Is Schematic ERC?">953</a></sup><sup class="cite"><a href="#src-253" title="EEVblog #253 - KiCAD Install &amp; Schematic - First Impressions">253</a></sup> Many companies enforce this as a formal gate: demonstrating a clean ERC is a precondition for moving to the PCB step.<sup class="cite"><a href="#src-953" title="EEVblog #953 - What Is Schematic ERC?">953</a></sup> Serious organisations treat this rigorously — "once bitten, twice shy" — and an ERC is regarded as a genuinely powerful tool rather than a formality.<sup class="cite"><a href="#src-953" title="EEVblog #953 - What Is Schematic ERC?">953</a></sup>

In practice the zero-error target is often reached by fudging: suppressing or overriding errors the designer believes they understand.<sup class="cite"><a href="#src-953" title="EEVblog #953 - What Is Schematic ERC?">953</a></sup><sup class="cite"><a href="#src-253" title="EEVblog #253 - KiCAD Install &amp; Schematic - First Impressions">253</a></sup> This is legitimate when the designer genuinely does know what the errors are, but it is a judgment call, and ignoring errors requires actually knowing what one is doing.<sup class="cite"><a href="#src-253" title="EEVblog #253 - KiCAD Install &amp; Schematic - First Impressions">253</a></sup>

The same caveat applies to the check as a whole. A report showing no errors proves only that the schematic satisfies the rules that were configured; the meaningfulness of the result rests entirely on the constraints set up beforehand.<sup class="cite"><a href="#src-1193" title="EEVblog #1193 - KiCAD PCB 4 Layer Swapping &amp; Stackup">1193</a></sup> A board can be riddled with problems and still produce a clean report — the appropriate response to a vendor's clean report is to ask to see the constraints.<sup class="cite"><a href="#src-1193" title="EEVblog #1193 - KiCAD PCB 4 Layer Swapping &amp; Stackup">1193</a></sup>

## Dependence on library quality

The quality of an ERC is only as good as the quality of the component libraries feeding it.<sup class="cite"><a href="#src-953" title="EEVblog #953 - What Is Schematic ERC?">953</a></sup> The check reasons about pin types, so pins must be correctly declared as input, output, open collector, bus, power, and so on in the symbol; a data-out pin declared as something other than an output will not trigger the output-to-output rule.<sup class="cite"><a href="#src-953" title="EEVblog #953 - What Is Schematic ERC?">953</a></sup> Once pin types are corrected in the library and the change is pushed through, the corresponding errors disappear from the report.<sup class="cite"><a href="#src-953" title="EEVblog #953 - What Is Schematic ERC?">953</a></sup>

No rule check can detect a pin that has been mislabelled in the library — pin 20 entered as pin 19 will pass every electrical rule while being electrically wrong.<sup class="cite"><a href="#src-953" title="EEVblog #953 - What Is Schematic ERC?">953</a></sup> This is why companies invest in dedicated library designers and freeze verified libraries permanently once validated.<sup class="cite"><a href="#src-953" title="EEVblog #953 - What Is Schematic ERC?">953</a></sup> The principle is "Garbage in, garbage out."<sup class="cite"><a href="#src-953" title="EEVblog #953 - What Is Schematic ERC?">953</a></sup> Nor can the tool detect errors of intent: swapping two nets while rearranging a schematic for tidiness produces a perfectly legal circuit that does the wrong thing, and ERC in CAD programs is not magic — "They can't cater for fires up in the gray matter."<sup class="cite"><a href="#src-240" title="EEVblog #240 - Power Supply Design Part 8">240</a></sup> Knowing what an ERC is and is not capable of, given the information supplied to it, is part of using it.<sup class="cite"><a href="#src-953" title="EEVblog #953 - What Is Schematic ERC?">953</a></sup>

## The Altium 17 detection failure

A significant defect was identified in Altium Designer 17, in which deliberately introduced schematic faults went undetected.<sup class="cite"><a href="#src-5eJorvyA708" title="Altium Designer Serious ERC bug">•</a></sup> A test schematic containing two output pins shorted together, a floating input pair with no driving source, and a data output pin connected to ground was compiled; only the no-driving-source conditions were flagged.<sup class="cite"><a href="#src-5eJorvyA708" title="Altium Designer Serious ERC bug">•</a></sup> No warning or error was raised for the shorted outputs or for the output tied to a power net, despite the project's connection matrix explicitly configuring output-pin-to-output-pin as an error.<sup class="cite"><a href="#src-5eJorvyA708" title="Altium Designer Serious ERC bug">•</a></sup> The same omission occurred when the check was run from an output job.<sup class="cite"><a href="#src-5eJorvyA708" title="Altium Designer Serious ERC bug">•</a></sup>

The failure appears tied to compiling a single schematic document rather than the whole project; selecting the project produced correct results, which is why compiling the project is the recommended invocation.<sup class="cite"><a href="#src-y-NiyRvqfXc" title="Another Altium Designer ERC Bug">•</a></sup><sup class="cite"><a href="#src-953" title="EEVblog #953 - What Is Schematic ERC?">953</a></sup> The open question is where the document-level compile obtains its rules, since it is evidently not reading the project options.<sup class="cite"><a href="#src-5eJorvyA708" title="Altium Designer Serious ERC bug">•</a></sup>

The severity comes from the reporting path rather than the missed check alone: a PDF report showing a passed ERC can be handed to management as authorisation to proceed to layout while the schematic still contains gross faults capable of destroying the parts on power-up.<sup class="cite"><a href="#src-5eJorvyA708" title="Altium Designer Serious ERC bug">•</a></sup>
